# 위키 상세 규약

CLAUDE.md 의 요약 규칙에 대한 상세 버전. 판단이 애매할 때 이 문서를 따른다.

## 1. 프론트매터 필드

모든 wiki/ 페이지는 YAML 프론트매터로 시작한다. lint 스크립트(`scripts/lint-*.py`)와
`generate-daily.py` 가 이 필드명에 의존하므로 임의로 바꾸지 않는다.

### 공통 필드

| 필드 | 필수 | 값 |
|---|---|---|
| `type` | ✅ | `experiment` \| `lesson` \| `build` \| `concept` \| `source` \| `question` \| `project` \| `daily` |
| `title` | ✅ | 페이지 제목. 파일명과 일치시킨다 |
| `domain` | ✅ | 아래 도메인 목록에서 하나 이상 |
| `created` | ✅ | `YYYY-MM-DD`. **`source` 는 예외 — `ingested` 가 이 역할을 한다**(중복 필드를 만들지 않는다) |
| `updated` | ✅ | 내용을 고칠 때마다 갱신 |
| `tags` | | 자유 태그 배열. 관례 태그: `문제해결`(문제를 만나 해결한 experiment — 타입 분리 대신 태그로 모아본다, 2026-08-24. 쌓이면 허브 페이지로 집계) |

### 타입별 추가 필드

- `experiment`: `status` = `running` / `done` / `abandoned` / `paused`
- `lesson`: `confidence` = `tentative`(근거 1개) / `working`(근거 2~3개) / `solid`(반례를 찾아봤고 견뎠음).
  선택 필드 `superseded_by` = 이 배움의 자리를 가져간 페이지 위키링크 (§5 하향 경로 참조).
  **방치는 필드로 선언하지 않는다** — 마지막 강화 시점은 인용 관계에서 계산되는 값이라
  `scripts/lint-lessons.py` 가 잡는다. 계산할 수 없는 것(대체)만 선언한다
- `build`: `status` = `idea` / `wip` / `shipped` / `archived`, `repo` = URL 또는 로컬 경로
- `concept`: `maturity` = `stub` / `growing` / `stable`. 사다리 밖 — 어휘·허브 (§5)
- `source`: `source_file`(`raw/<분류>/<파일명>` 전체 경로), `source_type`, `author`, `ingested`
- `question`: `status` = `open` / `answered` / `dropped`. answered 가 되면 답을 이 페이지의 「답」 섹션에 적는다 — 소속 없는 종합 답변의 집 (구 synthesis 역할, 2026-08-24)
- `daily`: 추가 필드 없음. 파일명·`title` 이 `YYYY-MM-DD` (§3 파일명 규칙의 유일한
  wiki 예외 — 일지는 제목이 아니라 날짜로 찾는다). 상세는 §11
- `project`: `status` = `active` / `paused` / `done`, `period` = `YYYY-MM ~ [YYYY-MM]`.
  업무를 **프로젝트 단위로 관리**하는 허브 (2026-08-18 사용자 결정) — 승격 사다리 밖이다.
  build 가 산출물 하나라면 project 는 builds·experiments·sources 를 엮고
  「현재 상태(날짜 스냅샷, §10)」와 「다음 액션」을 담는 관리 단위.
  허브는 유지비용이 있으므로 **진행 중인 업무에만 만든다** — 끝난 업무는 필요해질 때 만든다.
  **프로젝트 이름은 사용자가 준다. LLM 은 매핑만 한다** (2026-08-18 확정) —
  구성요소·기간·연결은 기록에서 도출되지만 이름은 팀의 실제 용어라 기록 밖에 있다.
  첫 명명 때 5개 중 2개를 문서 제목에서 유추했다가 틀렸다("가드레일 개발"→
  프로젝트 A). 이름은 검색 키다 — 사용자 언어와 다르면 못 찾는다.
  LLM 이 프로젝트가 필요해 보이면 **이름을 지어서 만들지 말고 이름을 물어본다**.
  **계층**: 큰 프로젝트는 하위 트랙 프로젝트로 나눌 수 있다 (2026-08-18, 프로젝트 A 4분할이 첫 사례). **폴더로 담는다** — `wiki/projects/<부모명>/` 아래에 부모 페이지와
  트랙 페이지를 함께 둔다(폴더 노트 방식). 파일명은 폴더 안에서도 `부모명 — 트랙명` 을
  유지한다: 위키링크가 경로 없이 **파일명만으로** 해석되므로(§4) 이름이 짧아지면
  `[[input text]]` 처럼 모호해지고 다른 프로젝트와 충돌한다. 폴더는 탐색용, 파일명은 링크용이다.
  상·하위는 `parent` 필드가 아니라 링크로 잇는다 (상위: / 형제: / 부모의 트랙 표).
  트랙별 현재 상태·다음 액션은 트랙 페이지가 담고 **부모는 트랙 표와 공통(가로지르는 것)만** —
  이중 기록은 드리프트가 된다.
  **프로젝트는 build 를 소유하지 않는다. 참조한다** (2026-08-18) — 프로젝트 중에 만든
  도구가 범용이면(공용 도구·최적화 루프) build 로 두고, build 페이지에
  「태생 프로젝트」를 적고 쓰는 프로젝트마다 링크를 건다. 도구를 project 로 승격하는 것은
  그 도구 자체에 독립 로드맵·다음 액션이 생겼을 때뿐이다
### 도메인 목록

`ai`, `work`, `dev`, `product`, `career`, `health`, `money`, `learning`, `life`

새 도메인이 필요하면 만들되, 이 목록에 추가하고 CLAUDE.md 에도 반영한다. 도메인이 15개를 넘으면 분류가 실패한 것이므로 통합을 제안한다.

## 2. raw/ 분류 — 취급 방식 기준

원본은 **어떻게 취급되는가**로 나눈다. 주제로는 나누지 않는다 — 주제 분류는 `wiki/` 의 일이다.

기본값은 **입수 경로(채널)** 다. 채널은 자명해서 분류 판단이 거의 0 이다: 대화면
conversations, Apple Notes export 면 notes, 업무 문서면 docs. 하지만 **취급이 갈리면
채널 안에서도 쪼갠다** — 실제로 폴더를 가르는 힘은 아래 세 질문이다 (2026-08-24 원칙 정정:
"채널로만 나눈다"는 문장이 실제 구조와 어긋나 있었다).

| 질문 | 갈리는 곳 |
|---|---|
| 공개해도 되나 | `external/`(추적) ↔ 나머지(로컬) |
| ingest 대상인가 | `personal/credentials/` 는 비대상 |
| 소화 방식이 다른가 | 논문(`external/papers/`) ↔ 아티클(`external/` 직속) — 같은 채널 안에서 쪼갠다 |

그래서 `credentials/`·`papers/` 는 최상위 채널이 아니라 **채널 안의 취급 구분**이고,
실제 위치도 채널 하위다 (`personal/credentials/`, `external/papers/`).
새 자료가 애매하면 **"이건 공개해도 되나 / ingest 하나 / 어떻게 읽나"** 를 먼저 묻는다.

| 폴더 | 채널 | git |
|---|---|---|
| `raw/conversations/` | 대화 발췌 — ingest 의 대화 원본 | 로컬 |
| `raw/notes/` | 내가 쓴 메모의 원본 — `inbox/` 에 직접 쓴 메모가 소화된 뒤 여기로 옮겨진다 (대화 발췌가 `conversations/` 로 가는 것과 같은 이치). 메모는 앱을 거치지 않고 inbox 에 직접 쓴다 (2026-08-24: 캡처 도구를 Obsidian 하나로 일원화) | 로컬 |
| `raw/docs/` | 외부 시스템에 있는 문서의 사본 — 회사 위키(Confluence) 등, **내가 쓴 것 포함** (소화용이거나, 내 소유가 아닌 시스템이라 잃기 싫은 것) | 로컬 |
| `raw/personal/` | 개인 민감 기록 — 연봉·평가·이력·검사 결과. 파일명은 **주제 접두사**: `YYMMDD-<주제>-slug` (예: `260824-연봉-계약서.md`) — 폴더 없이 검색·정렬로 모이게. 같은 주제 3개 이상이면 그때 폴더로 | 로컬 |
| `raw/personal/credentials/` | 내용이 키·비번·토큰뿐인 메모 — **ingest 비대상** | 로컬 |
| `raw/external/` | 외부 웹·일반 아티클·책 발췌 (그 자료의 그림도 함께) | **✅ 추적** |
| `raw/external/papers/` | 논문 클리핑 — 소화 방식이 달라 채널 안에서 구분 | **✅ 추적** |
| `raw/assets/` | 다른 채널 문서가 참조하는 이미지·첨부 — 다이어그램·스크린샷·PDF | 로컬 |

- 공개 경계는 규칙 한 줄: **외부 공개물 채널(external) 하나만 추적, 나머지 전부 로컬.**
  (2026-08-24 개편: 논문을 최상위 채널이 아닌 `external/papers/` 하위 폴더로 —
  취급(추적·파일명)이 같고 소화 방식만 달라, credentials 처럼 채널 안에서 구분)
  `assets/` 를 로컬로 둔 이유(2026-08-18 정정): 업무 문서가 **텍스트면 로컬인데
  스크린샷이면 공개**되는 구멍이 생긴다. 이미지는 마스킹도 어렵다. 공개해도 되는
  첨부는 `external/` 에 원문과 함께 둔다.
- Obsidian 첨부 경로도 `raw/assets` 로 설정돼 있다(`.obsidian/app.json`) — 노트에
  이미지를 붙여넣으면 볼트 루트가 아니라 여기 떨어진다. 규약과 도구를 맞춰둔 것이다.
- ⚠️ **살아 있는 디렉토리를 통째로 복사하지 않는다** (2026-08-18 확정).
  `raw/` 는 불변 원본 계층인데, 위쪽에 계속 갱신되는 원본이 따로 있으면 복사본은 뜬
  순간부터 낡는다 — §10 이 말하는 **포인터로 둘 것**의 사례다.
  (사례: Claude Code 메모리 디렉토리를 통째로 백업했다가 **3일 만에 원본과 어긋났다**.)
  일괄 복사 대신, 한 건이 오래 갈 배움이 되면 그때 개별 소화한다(§6).
- `personal/` 은 채널이 아니라 **취급 예외**다 — 어느 채널로 왔든 개인 민감 기록이면
  여기로. `credentials/` 는 그 하위로, 값을 위키에 절대 옮기지 않고 "여기에 있다"만
  적는다 (CLAUDE.md 정보 취급).
- `credentials/` 는 **저장소가 아니라 격리망**이다 — 시크릿의 집은 패스워드
  매니저·키체인이고, 이 폴더는 export·이관에 **섞여 들어온** 시크릿 메모를 가두는
  곳이다 (볼트는 평문이라 새 시크릿을 여기 적지 않는다).
- 그래도 애매하면 사용자에게 한 번 묻는다. 잘못 넣으면 `raw/` 는 이동 금지라 정정이
  번거롭다. (이동이 꼭 필요하면 사용자 승인을 받고 옮긴 뒤 참조하는 페이지를 모두 갱신한다.)
- **예외 — 회사 위키 문서(`-wiki.md`)는 `raw/docs/` 가 아니라 `wiki/projects/<프로젝트>/wiki/`
  폴더 안에 원문 그대로 둔다** (2026-08-25 확정). 그 프로젝트가 실제로 만들어 회사 위키에
  게시한(또는 게시 예정인) 문서라 프로젝트 페이지 바로 옆에서 열어볼 수 있어야 하기
  때문 — `raw/docs/` 에 묻히면 찾기 어렵다. 프로젝트 페이지 파일과 같은 층에 두지 않고
  하위 `wiki/` 서브폴더에 모으는 이유는, 회사 위키 문서가 여러 개면 프로젝트 폴더를 열었을 때
  전부 한꺼번에 나열돼 정작 프로젝트 페이지를 찾기 번거워지기 때문이다. 파일 첫 줄에
  `> 회사 위키 문서 원본 — …` 마커를 반드시 남긴다(`scripts/lint-frontmatter.py`·
  `lint-links.py`·`lint-index-stats.py`·`lint-freshness.py` 가 이 마커로 프론트매터·위키링크·
  페이지 집계·신선도 검사를 예외 처리한다 — 이 문서들은 외부 시스템의 냉동 스냅샷이라
  "재관측"의 대상이 아니다). 진짜 정본은 여전히 원본 레포(예: `<프로젝트 레포>/docs/`)에
  있고, 이 파일은 그 스냅샷이다 — 위키 갱신은 원본 레포 파일을 고쳐 다시 게시하는 것이
  정본 절차다(전역 CLAUDE.md 회사 위키 게시 규칙과 동일). 프로젝트 페이지 자체는 폴더
  노트 방식으로 `wiki/projects/<프로젝트>/<프로젝트>.md`에 둔다(§3.1) —
  `[[프로젝트명]]` 위키링크는 파일명만 보므로 안 깨진다.
- **변형 — 로컬 레포 원본이 아예 없는 경우** (2026-08-25 추가): 위 예외는 "로컬에서 먼저 고치고
  게시하는" 문서를 전제하지만, **이미 게시된 Confluence 페이지를 그대로 가져오는** 경우도 있다
  (예: 회사 위키를 순회하며 관련 트리를 통째로 pull). 이때는 로컬 레포 원본이 없으므로 마커
  문구가 달라진다 — "정본은 여전히 원본 레포"가 아니라 **"정본은 Confluence 그 자체
  (pageId 명시), 로컬 레포 원본 없음"**. 이 파일이 곧 유일한 로컬 사본이 되고, 이후 고칠 일이
  생기면 **이 파일을 먼저 고치고 리뷰 → 확정 → 재게시**하는 것이 그 시점부터의 정본 절차가
  된다(전역 CLAUDE.md 규칙과 동일하게, 이 순간부터 이 로컬 파일이 신규 정본 역할). 배치
  방식(`wiki/projects/<프로젝트>/wiki/`)·lint 예외는 위와 동일하다. 컨테이너 페이지(자식
  목록만 있고 본문이 없는 상위 노드)는 별도 파일로 두지 않고 소스 페이지·프로젝트 페이지에
  구조만 요약해 반영한다 — 실질 내용이 없는 파일을 늘리지 않기 위함.

## 3. 파일명 규칙

- 한국어 제목을 그대로 파일명으로 쓴다. Obsidian 위키링크가 파일명 기반이라 검색과 링크가 자연스러워진다.
- `raw/` 만 예외: `YYMMDD-slug.md` 로 날짜 접두사를 붙인다. 시간순 정렬과 중복 방지가 목적.
  (2026-08-19 `YYYY-MM-DD` → `YYMMDD` 로 변경 — 레포·브랜치 관례와 통일. 기존 200개 일괄 리네임 완료.
  프론트매터의 `created`·`updated` 와 `daily/` 파일명·`log.md` 표기는 그대로 `YYYY-MM-DD` 다 —
  그쪽은 `generate-daily.py` 가 날짜로 파싱하는 데이터 필드라 ISO 형식을 유지한다.)
- 파일명에 `/`, `:`, `#`, `^`, `|`, `[`, `]` 를 쓰지 않는다 (Obsidian 링크 문법과 충돌).

**`raw/` 날짜 접두사의 예외 2개** (2026-08-24 명시 — 실제로 이렇게 운영되고 있었다):

- `raw/docs/` 는 **원본 시스템의 페이지 ID** 를 접두사로 쓴다(예: Confluence pageId). 날짜보다
  안정적인 식별자이고, 원본 페이지를 다시 찾는 키가 된다.
- 다른 시스템을 미러링한 폴더는 **원본 파일명을 유지한다** —
  이름을 바꾸면 원본과 대조가 안 돼 미러가 무의미해진다.

예외는 이 둘뿐이다. 그 외 채널에서 접두사 없는 파일이 보이면 리네임 누락이다.

### 3.1 폴더로 묶기 (2026-08-18 확정)

**형제 페이지가 3개 이상 같은 접두사를 공유하면 폴더로 담는다.** 부모가 있으면 부모도
같은 폴더에 넣는다(폴더 노트 방식).

```
wiki/projects/프로젝트 A/     ← 부모 + 트랙 4
wiki/1-sources/Mac 메모/                  ← 시대별 3
wiki/1-sources/회사 위키/                 ← Confluence 4
```

- **파일명은 줄이지 않는다.** 위키링크는 경로 없이 파일명만으로 해석되므로(§4),
  폴더 안이라고 이름을 줄이면 `[[input text]]` 처럼 모호해지고 다른 묶음과 충돌한다.
  **폴더는 탐색용, 파일명은 링크용**이다 — 둘의 역할이 다르므로 중복이 아니다.
- 그래서 폴더로 옮겨도 **링크는 하나도 안 깨진다.** 이동 비용이 사실상 0이라,
  묶임이 보이면 그때 옮기면 된다.
- 3개 미만이면 만들지 않는다. 폴더가 페이지보다 많아지면 탐색이 더 나빠진다.
- `index.md` 는 폴더를 반영하지 않는다 — 카탈로그는 이름으로 찾는 것이고
  경로는 링크에 안 들어가기 때문이다.

## 4. 링크 규칙

- 페이지 간 연결은 반드시 `[[페이지명]]` 위키링크로. 마크다운 `[텍스트](경로)` 는 외부 URL 에만 쓴다.
- **위키링크에는 경로를 붙이지 않는다** — `[[공용 도구]]` 이지 `[[wiki/builds/공용 도구]]` 가 아니다.
  파일명이 볼트 전체에서 유일하므로 경로가 필요 없고, 붙이면 lint 가 대상을 못 찾아
  **깨진 링크 + 고아 페이지로 동시에 잡힌다**
  (2026-08-17 Obsidian 자동 링크 갱신으로 18곳에 접두사가 붙어 페이지 2개가 고아가 됨).
- **모든 페이지는 최소 1개의 인바운드 링크를 가져야 한다.** 새 페이지를 만들면 반드시 어딘가에서 링크를 걸어준다. 고아 페이지는 존재하지 않는 것과 같다.
- 아직 없는 페이지로 링크를 거는 것은 허용된다 — 다음에 쓸 것의 예약이다. lint 때 목록으로 보고한다.
- 링크에는 맥락을 붙인다. `[[프롬프트 캐싱]]` 만 두지 말고 `[[프롬프트 캐싱]] 을 적용해 비용이 절반이 됐다` 처럼 관계가 드러나게 쓴다.

## 5. 승격 규칙 (이 위키의 핵심 동학)

경험이 쌓이면 추상화 단계를 올린다. 이게 단순 일지와 세컨드 브레인을 가르는 지점이다.

```
raw (사실 — 불변 원본)
    ↓ 소화되면
근거 페이지 — source(읽은 것) · experiment(해본 것) · 대화 발췌 인용
    ↓ 독립된 근거 2건이 하나의 주장을 지지하면 (근거의 출처 종류는 무관)
lesson (일반화된 배움)
```

### 근거 2건은 필요조건이지 충분조건이 아니다 (2026-08-25 추가)

근거 개수를 세는 것만으로는 **격언이 통과한다.** 승격 전에 주장의 형태를 먼저 본다:

- **반증 가능한가** — 무엇이 관측되면 이 주장이 틀린 것이 되는지 말할 수 있어야 한다.
  말할 수 없으면 그건 배움이 아니라 옳은 말이다.
- **몰랐다면 다르게 행동했을 것인가** — 이 문장을 읽고 바뀌는 판단이 없으면 페이지로 둘 이유가 없다.

둘 중 하나라도 걸리면 승격하지 않는다. 근거가 몇 건이든 마찬가지다.

(사례: 2026-08-25 「실측이 설계를 이긴다」를 근거 3건·도메인 독립까지 갖춰 승격했다가
철회했다. 적용 조건과 한계·반례까지 채웠는데도 **핵심 주장 자체가 반증 불가능한 격언**이었다.
템플릿 주석의 "적용 조건이 없으면 격언이 된다"는 경고로는 이 경우가 안 걸린다 — 조건을
붙여도 격언일 수 있다. 근거를 세기 **전에** 주장을 본다.)

**concept 은 사다리 밖이다** (2026-08-24 개편). 증류의 종착지가 아니라 **어휘·허브** —
링크의 교차점이 필요한 용어·구조에 자유 생성한다 (승격 조건 없음). 가치는 역링크에
있다: `[[RAG]]` 를 언급하는 모든 페이지가 링크하면 그 역링크가 "이 주제에 대해 내가
아는 전부"를 자동 집계한다. 여러 lesson 이 한 구조를 가리켜 이름을 붙이는 경우
(`비대칭 강화` 류)도 concept 의 탄생 경로 중 하나지만 의무 관문이 아니다.
(개편 근거: karpathy 원안·참고 구현체 전부가 concept 을 자유 생성 허브로 쓰고,
10일 실측의 concept 11개도 대부분 어휘로 태어났다 — "lesson 수렴" 문은 장식이었다.)

(2026-08-24 수정: 구 조건 "experiment 2회 반복"은 실측과 어긋났다 — 10일 운영에서
lesson 24개 대부분이 소스·대화에서 직접 형성됐고 experiment 는 4개뿐. 실제 경로인
"출처 무관 근거 2건"으로 교체. experiment 는 1차 경험이라 **가장 강한 근거**지만
유일한 경로가 아니다.)

- **인용은 2단이다**: 근거가 페이지로 존재하면(`source`·`experiment`) `[[페이지]]` 로
  링크한다 — 링크 그래프에 잡혀야 역링크·lint(방치 계산)가 작동한다. 근거 페이지를
  만들 가치가 없는 가벼운 근거는 lesson 본문에 `근거 발췌: raw/<경로>` 한 줄로 직접
  가리킨다 — 이것도 정식 경로다. raw 는 항상 사슬의 바닥이다(페이지가 raw 를 가리킨다).
- 승격할 때 원본 페이지를 지우지 않는다. 링크로 잇는다. 근거가 사라지면 배움은 격언이 된다.

### 하향 경로 — 배움이 죽는 세 가지 방식

사다리에는 내려가는 길도 있어야 한다. 올라간 `lesson` 은 셋 중 하나로 죽는다:

- **반박됨**: 새 경험이 뒤집는다 → `confidence` 를 낮추고 **반례 항목에 기록한다.**
  지우지 않는다. 틀렸던 기록이 가장 값지다.
- **대체됨**: 더 나은 배움이 자리를 가져간다 → 프론트매터에 `superseded_by: "[[새 페이지]]"` 를
  선언하고, 옛 페이지를 인용하던 곳을 새 페이지로 옮긴다. 옛 페이지는 남는다.
- **방치됨**: 아무도 다시 쓰지 않는다 → 선언하지 않고 **계산한다.**
  마지막 강화 = max(자기 `updated`, 이 페이지를 인용한 페이지들의 `updated`).
  `scripts/lint-lessons.py` 가 180일 넘게 강화 없는 lesson 을 보고하면
  유효(그대로) / 대체(`superseded_by`) / 보관 중 하나를 사람이 정한다.

### 모순인가, 진화인가

두 페이지가 충돌할 때 바로 한쪽을 고치지 말고 먼저 구분한다:

- **진화**: 내가(또는 근거가) 마음을 바꾼 것 — 모순이 아니라 성장이다.
  현재 입장으로 갱신하되 페이지에 `## History` 항목을 남긴다:
  `예전엔 X 라고 적었음(근거, 날짜) → Y 로 갱신(새 근거, 날짜)`. 경로를 지우면
  "왜 이렇게 생각하게 됐나"를 다음 세션이 답할 수 없다.
- **진짜 모순**: 판정 기준은 둘 — 어느 쪽이 **더 새로운가**(날짜),
  어느 쪽이 **더 권위 있는가**(1차 경험 > 업무 문서 > 외부 아티클 > 전언).
  승자가 분명하면 진 쪽에 반례로 기록하고 이긴 쪽으로 갱신한다.
- **판정 불가**: 억지로 정하지 않는다. 양쪽 근거를 적은 `question` 페이지로 열어두고
  두 페이지에서 링크한다 — 위키가 스스로 모르는 것을 아는 상태가 낫다.

위키는 서로 모순되는 두 페이지를 **모순인 줄 모른 채** 가지고 있으면 안 된다.
모순은 해소되거나, 명시적으로 열린 질문이 된다.

## 6. Ingest 상세 절차

**여러 프로젝트에 걸친 대량 소화는 그룹 단위로 나눈다** (2026-08-25 확정): inbox 파일이
많고(대략 10건 이상) 서로 다른 프로젝트·레포에 걸쳐 있으면 한 번에 다 처리하지 않는다 —
항목이 많을수록 5단계(기존 페이지 대조)가 부실해져 중복·모순을 놓치기 쉽다. 소속
프로젝트·레포 단위로 나눠 한 그룹씩 1~9단계를 끝까지 밟고, 그룹 하나가 끝날 때마다
(등재·log·lint 통과까지) 사용자에게 보고한 뒤 다음 그룹으로 넘어간다. 한 그룹 자체가
10건을 넘으면 그 안에서도 다시 작게(예: 날짜순 10건 단위) 나눈다. 파일 몇 개뿐이거나
전부 같은 프로젝트면서 10건 이하면 나눌 필요 없다.

0. **받는 즉시 원본을 `inbox/` 에 저장한다 — 판단 0개** (2026-08-18 확정).
   대화·파일·URL 어느 경로로 왔든 같다. 목적은 중단 안전망이다: 소화가 끊겨도
   자료가 inbox 에 남고, inbox 잔량이 곧 미처리 백로그다. 사용자가 대화 밖에서
   inbox 에 직접 던진 파일은 이 단계가 이미 끝난 것이다.
1. 분류(§2)를 정해 `raw/` 의 **알맞은 분류 폴더**로 이동한다 (날짜 접두사 파일명,
   프론트매터에 출처 기록). 분류가 애매하면 이동 전에 사용자에게 묻는다 —
   착지(0)는 질문을 기다리지 않고, 판단이 필요한 이동(1)만 기다린다.
   - **예외 — "-wiki.md" 파일이 `wiki/projects/<프로젝트>/wiki/` 에 이미 있는 파일의
     새 버전이면, `raw/` 로 보내지 않고 그 자리에서 덮어쓴다** (2026-08-25 확정). 회사
     위키 게시 워크플로가 "로컬 원본 수정 → 게시"라, 그 프로젝트 세션이 끝날 때마다
     SessionEnd 훅이 그 로컬 원본을 `inbox/` 에 자동으로 떨군다 — 이게 곧 "위키 갱신됨"
     신호다. 파일명(날짜 접미사 포함)으로 기존 스냅샷을 먼저 찾고, 있으면 덮어쓴 뒤
     `> 회사 위키 문서 원본 — …` 마커와 날짜만 갱신한다(내용은 새 버전 그대로). 이
     경로면 2~9단계(소스 페이지·기존 페이지 갱신 등)는 실제 내용 변경분에 대해서만
     가볍게 수행 — 매번 전체를 새로 소화하지 않는다. 기존 스냅샷이 없으면(최초
     ingest) §2 의 일반 절차(신규 배치)를 그대로 따른다.
2. 원본을 끝까지 읽는다. 요약본이 아니라 원본을.
3. 사용자와 핵심 takeaway 를 짧게 논의한다. 이때 **사용자의 반응 자체가 위키 콘텐츠**다 — 어디에 동의하고 어디에 걸렸는지 기록한다.
4. `wiki/1-sources/` 에 소스 페이지를 쓴다.
5. 영향을 받는 기존 페이지를 **찾아서** 고친다. 이 단계가 ingest 의 본체다. 새 페이지만 쓰고 기존 페이지를 안 고치면 그냥 파일 더미가 된다.
6. 새로 필요한 개념 페이지를 만든다.
7. `index.md` 에 신규 페이지를 등재한다.
8. `log.md` 에 한 줄 추가한다.
9. 사용자에게 **무엇이 바뀌었는지** 보고한다 — 만든 페이지, 고친 페이지, 발견한 충돌.
   **버릴 후보(쓸모없음·완전 중복)는 여기서 일괄 확인한다** (2026-08-24 확정):
   "버릴 후보 N개: (목록·사유). 지울까?" — 확인이 떨어지면 inbox 에서 즉시 삭제한다.
   raw 로 옮기지 않는다 (raw 는 근거가 될 원본만). 내용은 안 남기되 처분 사실만
   log.md 의 ingest 항목에 한 줄 남긴다 ("버림 N건: 사유"). 확인 전까지 inbox 에
   남는 건 어쩔 수 없지만, 낱개로 묻지 말고 **배치로 한 번만** 물어 잔류를 최소화한다.
   내용이 이미 위키에 있는 중복이면 버리기 전에 어느 페이지에 있는지 알려준다.

**소화는 raw 까지가 아니라 wiki 까지다** (2026-08-18 사용자 지적). `raw/` 에 옮겨두고
끝내면 그건 보관이지 소화가 아니다 — 원본은 자기가 안 읽혔다고 말하지 못한다.
`scripts/lint-raw-coverage.py` 가 **wiki 가 가리키지 않는 raw 원본**을 잡는다.
대량 채널(notes)은 배치 소스 페이지로 커버되고, 나머지는 파일 단위로 본다.

### 6.1 라우팅 — 어느 타입으로 갈 것인가

4~6단계(소스 페이지·기존 페이지 수정·개념 페이지)에서 쓰는 판단표다. 원본이 파일이든
대화든(§7 Query 4단계) 같다. **위에서부터 먼저 걸리는 것을 택한다.**

| 내용의 성격 | 행선지 |
|---|---|
| 기존 페이지에 있어야 할 보강·정정 | **그 페이지를 고친다. 새 페이지 금지** |
| 하나의 주장으로 압축 + 근거 2건 이상 | `lesson` (단 §5 주장 형태 필터를 통과해야 한다) |
| 링크 교차점이 필요한 용어·구조 | `concept` |
| 답이 아니라 못 푼 질문이 드러남 | `question` |
| 내가 해본 시도의 기록 | `experiment` |
| 여러 페이지를 엮은 답변 | 전용 타입 없음 — 소속 있으면 그 `project`·`build` 에, 소속 없이 재사용될 답이면 `question` 에 답을 적고 `answered` 로 (2026-08-24 syntheses 폐지: 세 행선지가 역할 전부 커버) |

|---|---|

사용자가 직접 던진 파일은 **건드리지 않는다** — 어디서 온 무엇인지 물어야 하고,

**한다** (1~4단계 + 부기): raw 이동 · 원본 통독 · 세션 단위 배치 소스 페이지 생성 ·

**하지 않는다**:

- **5단계(영향받는 기존 페이지 수정)** — ingest 의 본체지만 판단이다. 무인이 기존 문장을
  고치면 원래 뭐였는지 되짚을 근거가 안 남는다. 1~4단계는 **더하기**라 되돌리기 쉽고
  (새 페이지를 지우면 끝), 5단계는 **고치기**라 다르다
- 페이지 삭제 · inbox 파일 버리기 · `lesson` 의 confidence 변경

**실행 권한** (2026-08-26 첫 실행에서 배운 것): `--permission-mode acceptEdits` 는 파일
편집만 자동 승인하고 **Bash 는 승인하지 않는다.** 그래서 첫 실행이 마무리 검증(`lint_all.py`)도
커밋도 못 하고 끝났다 — 게이트 없이 산출물만 남은 셈이다. `--allowedTools` 로 필요한
명령만 사전 승인한다: `lint_all.py` · `lint_autofix.py` · `git add/commit/status/mv` · `mv` · `ls`.
**넓게 열지 않는다** — 무인 세션이 임의 명령을 실행할 수 있게 되면 이 권한 설계가 무의미해진다.

**넘기는 방식**: 5단계 후보를 그날 일지 **「볼트」**에 **한 줄로** 남긴다 (§11 — 「이슈」는 사람의 업무 이슈 전용) —
`- [ ] ingest(날짜): 세션 N건 소화됨 — [[배치 소스]] / 영향 후보: [[A]] · [[B]]`
사람이 그 줄을 보고 지시하면 그때 대화형으로 5단계를 수행한다. 아침에 4단계까지 끝나 있으므로
사람이 하는 일은 0단계가 아니라 마지막 단계뿐이다.

**사람이 기억할 필요는 없다** — 세션 시작 훅(`vault_backlog_hook.py`, machine-setup §6.1)이
어느 폴더의 세션이든 열릴 때 이 줄을 컨텍스트로 올리고 처리할지 묻는다. 체크박스를 승인
신호로 쓰지 않는 이유도 같다: 그건 사람이 옵시디언을 열어 체크하는 걸 기억해야 도는 구조라
"절차 준수가 기억력에 달려 있으면 샌다"는 문제를 되풀이한다. `[x]` 는 계속 **완료** 표시다.

세션 시작 훅이 이 줄도 같이 올린다 (§6.2 말미 · machine-setup §6.1) — 줄머리
`lint(`/`ingest(` 로 담당 스킬이 갈린다.

**기록**: `log.md` 에 `## [YYYY-MM-DD] lint | 무인 실행`, 커밋 메시지는 `auto-lint |`
로 시작한다 — 사람이 되돌릴 지점을 찾기 쉽게.

### 보고 형식 (2026-08-25 추가)

평평한 나열은 깨진 링크 1건과 승격 후보 1건을 같은 무게로 보이게 한다. **심각도 3단계로
묶어 그 순서대로** 보고한다:

1. **깨짐** — 지금 위키가 틀린 것. 깨진 링크·프론트매터 결손·현황 숫자 불일치·선언 불일치.
   기계 검사가 잡은 것은 거의 다 여기다
2. **낡음** — 문장은 멀쩡한데 참이 아닌 것. 노후 lesson·낡은 스탬프·소화 미완·stub 방치.
   **조용한 실패 계열이라 안 찾으면 영원히 안 보인다**
3. **후보** — 아직 없는 것. 승격 후보·이름 없는 구조. 깊게 파려면 `wiki-emerge` 로 넘긴다

각 항목은 `파일 — 무엇이 틀렸나 — 고치면 어떻게 되나` 한 줄로 쓴다. 기계 검사가 잡은 건
스크립트 이름을 같이 적어 재현 가능하게 한다. 깨끗하면 **짧게 깨끗하다고만** 한다 —
분량을 채우려고 3번을 억지로 만들지 않는다.

## 9. LLM 이 하지 말아야 할 것

- `raw/` 안의 파일을 수정·삭제·이동하지 않는다. 읽기 전용이다.
- 사용자가 1인칭으로 쓴 회고·감정·판단을 매끄럽게 고쳐 쓰지 않는다. 그건 원본 데이터다.
- 근거 없는 내용을 위키에 쓰지 않는다. 추론이면 추론이라고 표시한다.
- 페이지를 삭제하지 않는다. 폐기는 `status: archived` 또는 `dropped` 로 표시한다.

## 10. 사실의 신선도

배움과 개념은 안 썩지만 **휘발성 사실**(가격·한도·쿼터·버전·인원·대기 상태)은 썩는다.
문제는 썩은 줄이 여전히 참처럼 읽힌다는 것 — `업로드 한도는 10MB다` 는 다음 분기에
조용히 거짓말이 되지만 문장은 그대로다.
(출처: obsidian-second-brain 의 OKM freshness 정책, 2026-08-18 채택)

**위키에 적히는 모든 사실은 셋 중 하나여야 한다:**

1. **무시간(timeless)** — 안 썩으므로 날짜가 필요 없다.
   `쿼터는 플랫폼 콘솔에서 신청한다` 처럼 구조·방법·판단 기준.
2. **스냅샷(snapshot)** — 날짜가 박힌 관측. `2026-08-14 실측: 커밋까지 5분` 은
   그날 참이었다는 주장이라 영원히 낡지 않는다. **날짜가 박힌 헤딩 아래는
   전부 자동으로 스냅샷이다** — log.md 와 experiment 의 타임라인이 이 경우.
3. **포인터(pointer)** — 현재 값이 중요한 사실은 값 대신 **진실이 사는 곳**을 적는다.
   `진실이 사는 곳: 플랫폼 콘솔 > Quota. 마지막 관측: GPU 8장 (2026-08-18)` —
   값은 선택이고, 붙이면 반드시 스탬프와 함께.

**유일한 불법 형태**: 날짜 컨테이너 밖에서 스탬프 없이 휘발성 사실을 현재형으로
주장하는 것. 쓸 때 스탬프 `(2026-08-18 기준)` 를 붙이거나 포인터로 바꾼다.

`scripts/lint-freshness.py` 가 검사한다 (창 기본 90일). 낡은 스탬프(FRESH-2)는
셋 중 하나로 처리한다 — **재관측**(값·스탬프 갱신) / **포인터로 변환**(아무도
재관측 안 하면 값이 중요하지 않았던 것) / **은퇴**(역사로 가치 있으면 날짜 헤딩
아래로 옮겨 스냅샷으로 만든다). 검사가 오탐이면 날짜를 붙여 스냅샷으로 만들거나
표현을 고친다 — 둘 다 위키가 좋아지는 방향이다.

## 11. 일지 (daily)

업무 기록을 날짜 단위로 남긴다 (2026-08-18 사용자 결정). `wiki/daily/YYYY-MM-DD.md`.
**대화로 말하면 내가 쓴다** — 사용자가 옵시디언을 직접 열지 않아도 되게 하는 것이 목적이다.

`log.md` 와 겹치지 않는다: `log.md` 는 **볼트 오퍼레이션** 이력(ingest·save·lint·setup),
일지는 **업무** 기록이다. 둘 다 시간순이지만 주어가 다르다.

### 섹션과 행선지

일지는 종착지가 아니라 **입구**다. 각 섹션은 갈 곳이 정해져 있고, 일지를 쓰면서
그 행선지를 같이 갱신하지 않으면 일지는 무덤이 된다.

| 섹션 | 행선지 |
|---|---|
| 일정 | 그날의 맥락. **캘린더 연동 자리**(아래). 스냅샷이라 갱신하지 않는다 |
| **해야할일** | 체크박스. 미완료는 다음날로 **이월**(아래) |
| 작업 | → 관련 `build`·`experiment` 페이지 갱신 |
| **정해진 것** | → 해당 `project` 의 「현재 상태」·「다음 액션」에 반영 **(본체)** |
| 이슈 | → 같은 이슈가 2회 반복되면 `question` 또는 `lesson` 후보 (§5). **사람의 업무 이슈 전용** |
| **볼트** | 자동화 전용 칸. 08:00 무인 ingest·08:30 무인 점검이 **행동이 필요한 것만 한 줄씩** 남긴다 |

**「이슈」와 「볼트」를 가르는 기준은 소유자다** (2026-08-26 신설). 무인 실행이 「이슈」에
쓰던 때 하루에 세 줄이 들어가 **업무 이슈 칸이 점검 로그가 됐다** — 매일 그러면 일지를
여는 이유가 사라진다. 기계는 「볼트」에만 쓰고, 상세는 `log.md` 에 두고 일지에는 사람이
행동해야 하는 것만 한 줄로 남긴다. 자동으로 고쳐진 것은 **아예 적지 않는다**(사람이 할 게
없으면 침묵). 빈 일지 판정(`prune_empty_past`)에서도 「볼트」는 제외한다 — 기계가 적은
줄은 "그날 기록이 있다"의 근거가 못 된다.

- **정해진 것 ≠ 해야할일.** 회의 결정은 상태 변화("benign-first 로 가기로 했다")이고
  할 일은 행동이다. 결정이 할 일을 낳으면 양쪽에 다 적되, 결정은 프로젝트로 흘려보낸다.
- **빈 섹션은 지운다.** 안 쓴 섹션이 남으면 노이즈다.
- 「배운 것」 섹션은 두지 않는다 — 배움은 하루가 아니라 **반복**에서 나온다(§5).
  매일 채우려 들면 억지 교훈이 쌓인다. 이슈의 반복이 lesson 으로 가는 정상 경로다.
- 일지에서 바로 `lesson` 을 만들지 않는다. 후보로 표시만 하고 승격은 `wiki-emerge` 의 일.

### 일정 — 캘린더 연동 (2026-08-24 완료)

「일정」은 **캘린더에서 자동으로 채운다** (2026-08-18 결정, 08-24 연동).
CalDAV 플러그인이 `캘린더/YYYY-MM.md` 에 월 단위 일정을
동기화하므로(5분 주기), `wiki-daily` 가 일지를 만들 때:

- `캘린더/<그 달>.md` 의 `## YYYY-MM-DD` 섹션을 읽어 시각·제목으로 적는다.
  단 **19:00 이후 시작 일정은 제외** — 저녁 개인 일정은 업무 일지에 안 담는다 (2026-08-24)
- **파일이나 그날 섹션이 없으면 조용히 건너뛴다** — 오류를 내거나 추측으로 채우지 않고,
  사용자가 말해준 일정만 적는다

**해야할일·작업은 맥락별로 묶는다** (2026-08-25 사용자 결정): 그룹 레이블은 **볼드 텍스트 줄**(`**레이블**`),
그 아래 항목들, 그룹 사이 빈 줄 (2026-08-25 볼드 확정 — 가독성). 기계(generate-daily)는 이월할 때
그룹을 보존하고(미완료 항목이 있는 그룹만), 새 항목을 어느 그룹에 넣을지는 LLM 이
일지를 만질 때 정리한다 — 예약 주입분·훅 수집분은 일단 위에 얹히고 소화 때 묶인다.

**날짜 미정 대기 항목은 해야할일의 「대기」 그룹으로** (2026-08-25 사용자 결정):
조건에 걸려 시점이 미정인 일("X 확정되면 진행")도 해야할일에 넣고 계속 이월시켜
매일 보이게 한다 — 단 「대기」 그룹으로 분리해 오늘 실행할 것과
안 섞는다. 조건이 풀리면 일반 그룹(또는 예약)으로 옮긴다. (MM-DD~) 가 묵은 정도의
신호다. 대기 항목이 많아져 목록이 무뎌지면 프로젝트 「다음 액션」 방식으로 재검토.

**이슈 스윕과 예약함** (2026-08-25): 사용자가 「이슈」 등에 산문으로 적은 할일성
문장("~해야 함")을 LLM 이 일지를 만질 때 발견하면 — 오늘 일이면 「해야할일」
체크박스로, 미래 날짜가 달렸으면 볼트 루트 `예약.md`(`- YYYY-MM-DD 내용`)로 옮기고
원문에는 `(→ 해야할일)` / `(→ 예약)` 표식만 남긴다 (스냅샷은 안 지운다). 예약.md 의
항목은 그 날짜 아침 generate-daily 가 해당 일지 「해야할일」로 주입하고 제거한다 —
지난 날짜가 남아 있으면 다음 실행 때 오늘로 끌어온다. 기계는 형태(체크박스·날짜)만
다루고 문장 판단은 LLM 몫이라는 분업이다.

**빈 과거 일지는 자동 삭제된다** (2026-08-25): 지난 날짜인데 일정·해야할일·작업·
정해진 것·이슈가 전부 빈 골격이면 generate-daily 가 아침 실행 때 지운다 —
기록 없는 날의 빈 파일은 거짓 기록이다. 일정만 있어도 남긴다 (그날의 맥락).

일지 파일 자체도 자동으로 생긴다 (2026-08-24): `scripts/generate-daily.py` 가
launchd(`com.user.wiki-daily-gen`, 매일 07:00)로 돌며 **당일 일지를 만든다** —
일정(캘린더)과 직전 일지의 미완료 할일 이월을 담아서. 이미 있으면 신규 일정·이월만
병합한다 (있는 줄은 안 건드림, 멱등). (2026-08-25: D+7 선생성 철회 — 쓰임이 없었다.) `wiki-daily` 스킬의 역할은 파일 생성이
아니라 **그날의 작업·정해진 것·이슈를 채우고 프로젝트로 흘려보내는 것**으로 좁혀진다.

회의에서 나온 결론은 「일정」이 아니라 **「정해진 것」**에 적는다 — 일정은 있었다는 사실이고,
정해진 것은 그 결과다. 전자는 스냅샷이고 후자는 프로젝트로 흘러간다.

### 해야할일 — 체크박스와 이월

```markdown
## 해야할일
- [x] 이미지 API 스키마 확정
- [ ] CDN 구성 담당자에게 일정 확인 (08-15~)
```

- 완료는 `- [x]`. **체크박스 모양과 취소선은 CSS 스니펫**
  (`.obsidian/snippets/daily-task-strikethrough.css`)이 담당한다 —
  체크박스를 네모(`--checkbox-radius: 0`)로 만들고, 체크하면 텍스트에 취소선을 긋는다.
  Minimal 테마가 체크 항목을 흐리게만 해서 "무엇이 남았나"가 안 보이던 것을 고친 것.
  `appearance.json` 의 `enabledCssSnippets` 에 등록돼 있고, 스니펫 폴더는 git 추적
  대상이라 다른 기기에도 따라간다. 파일을 새로 만든 직후에는
  **설정 → 모양 → CSS 스니펫에서 새로고침(↻)** 을 눌러야 목록에 잡힌다.
- **이월**: 새 일지를 만들 때 **가장 최근 일지의 미완료(`- [ ]`) 항목을 그대로 가져온다.**
  「이어갈 것」 섹션을 따로 두지 않는 이유다 — 손으로 옮기면 체크박스와 이중 기록이 된다.
- 이월할 때 **처음 적힌 날짜를 `(MM-DD~)` 로 붙인다.** 며칠째 밀리는 일이 눈에 보이는 게
  이 방식의 진짜 이득이다. 이미 표시가 있으면 그대로 둔다(원래 날짜가 유지돼야 한다).
- **지난 일지는 고치지 않는다.** 어제 못 끝낸 일은 어제 일지에 미완료로 남는 게 사실이다.
- 이월된 항목이 5일 넘게 밀리면 일지가 아니라 **프로젝트 「다음 액션」이 있어야 할 자리**다 —
  그때는 프로젝트로 옮기고 일지에서는 뺀다.

### 링크 규칙 — 인바운드가 아니라 아웃바운드

일지는 **날짜로 찾는 페이지**라 §4의 인바운드 링크 요구에서 면제된다
(`log.md` 와 같은 이유). 대신 **아웃바운드를 요구한다** — 어느 프로젝트·산출물에도
안 닿는 일지는 위키 노드가 아니라 일기다. `scripts/lint-links.py` 가 양쪽을 다 본다.

`index.md` 에는 일지를 **개별 등재하지 않는다** — 날짜가 곧 주소이고, 365개를 나열하면
카탈로그가 무너진다. 「현황」의 집계 숫자에만 반영한다.

### 신선도

일지 파일 자체가 날짜 컨테이너라 **전체가 스냅샷**이다(§10 FRESH-4). 그날 참이었던
것을 적은 것이므로 낡지 않고, 나중에 고치지 않는다. 사실이 바뀌면 그날 일지를
고치는 게 아니라 **오늘 일지에 새로 적고 프로젝트 페이지를 갱신한다.**
